1. Hands-on check (before the quiz)
-----------------------------------
Build Release | x64, then run x64\Release\CSOPESY.exe from the repo folder (it reads
config.txt from the folder it runs in). Suggested run:
    initialize
    screen -s A        process screen; type process-smi a few times until "Finished!"
    exit               back to the main menu
    screen -r A        expect "Process A not found."
    scheduler-start    then wait about 10 seconds
    screen -ls         CPU utilization, cores, running and finished processes
    screen -r p05      then process-smi, then exit
    scheduler-stop
    report-util        writes csopesy-log.txt next to config.txt
    exit
Then change config.txt (for example num-cpu 1 and scheduler "fcfs"), restart, and compare.
Pace: one CPU tick is 10 ms, so a default process (1000-2000 instructions) needs about
20-40 seconds on a free core. Lower min-ins/max-ins to finish sooner; raise delay-per-exec
to slow processes down.

3. PPT technical report: required sections and where each lives in the code
---------------------------------------------------------------------------
- Command recognition: Console::handleCommand (src/Console.cpp). Splits the input into
  words, matches the command in any letter case, and refuses everything except
  "initialize" and "exit" until initialize has run.
- Console UI implementation: Console::run (prompt loop), printBanner, attach (process
  screens; the console clears when entering and leaving one), printProcessInfo
  (process-smi), utilizationReport (shared by screen -ls and report-util).
- Command interpreter implementation: Console::initialize, screenCreate, screenResume,
  screenList and reportUtil; scheduler-start and scheduler-stop call
  Scheduler::startBatchGeneration and stopBatchGeneration. Settings come from loadConfig
  (src/Config.cpp).
- Process representation: class Process (src/Process.h/.cpp) and Instruction
  (src/Instruction.h/.cpp). A process has an ID, a name, its creation time, its length N
  ("Lines of code"), how many instructions it has executed ("Current instruction line"),
  uint16 variables, its PRINT logs, and a stack of active FOR loops. Instructions are
  generated from the process's own seed as it runs, so exactly N execute. FOR loops nest
  at most 3 deep, and every pass through a loop body counts toward N.
- Scheduler implementation: class Scheduler (src/Scheduler.h/.cpp). A background thread
  runs one CPU tick every 10 ms. In each tick, every busy core runs one instruction (or
  one busy-wait tick of delay-per-exec); scheduler-start adds a process every
  batch-process-freq ticks; sleeping processes whose time is up rejoin the ready queue;
  and idle cores take processes from the front of the ready queue. FCFS never preempts.
  RR moves a process to the back of the queue after quantum-cycles ticks when another one
  is waiting. SLEEP(X) takes a process off its core for X ticks.

5. Behaviour decisions (useful when explaining results)
-------------------------------------------------------
- PRINT always logs "Hello world from <process name>!". SLEEP lasts 1-10 ticks. Variables
  are x, y and z, and values are clamped to 0-65535.
- screen -s on a running process opens it (the spec opens scheduler-made processes with
  screen -s); on a finished process it prints "Process <name> already exists."
- screen -ls lists the processes that are on a core under "Running processes". The times
  shown are creation times. Utilization shows two decimals when it is not whole
  (for example 66.67%).
- Also accepted, from the spec's own wording: delays-per-exec, scheduler-test, screen-ls,
  a quoted scheduler value, and commands in any letter case.
- Memory grows with the PRINT logs that process-smi has to keep: about 0.5 MB per second
  with 128 cores and nonstop scheduler-start, far less with the default config.
